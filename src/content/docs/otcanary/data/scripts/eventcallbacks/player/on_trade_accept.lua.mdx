## 💡 Tip

<Aside type="tip">
**Fluxo de Aceitar Trade (Trade Accept)**

Quando um jogador aceita uma trade proposta:

1. **Trigger:** Player clica "Accept Trade" button
2. **Ambos os Lados:** playerOnTradeAccept é disparado para player E target
3. **Cleanup:** Fecha Forge e Imbuement windows
4. **Validação:** Retorna true para confirmar
5. **Ação:** Trade é finalizada se ambos retornam true

**Exemplo de Fluxo - Trade entre Dois Jogadores:**
```
Player A propõe trade com 10 gold → Sword de Player B
Player B aceita → playerOnTradeAccept(B, A, 10gold, sword)
  ├─ B:closeForge()
  ├─ B:closeImbuementWindow()
  ├─ A:closeForge()
  ├─ A:closeImbuementWindow()
  └─ return true

Mesmas calls para Player A com parametros invertidos
  └─ playerOnTradeAccept(A, B, sword, 10gold)

Trade é executada: A perde sword, B ganha sword, etc.
```

**Diferença de on_look_in_trade.lua:**
- `on_look_in_trade` → Visualizar item DURANTE trade (observação)
- `on_trade_accept` → FINALIZAR trade (commit das mudanças)
</Aside>

## 📄 Visão Geral do Código (Resumo Executivo)

### Propósito Principal

O script `on_trade_accept.lua` implementa o callback de aceitação de trade. Quando um jogador aceita uma trade:

- **Limpa UI de ferramentas** (Forge e Imbuement windows)
- **Executa cleanup para ambos** os jogadores envolvidos
- **Confirma trade** retornando true

### Arquitetura

O script usa um padrão de **bilateral cleanup + confirmation**:

```
playerOnTradeAccept (entrada)
  ├─ player:closeForge()
  ├─ player:closeImbuementWindow()
  ├─ target:closeForge()
  ├─ target:closeImbuementWindow()
  └─ return true (confirma trade)
```

### Fluxo Lógico Resumido

| Entrada | Processamento | Saída |
|---------|---------------|-------|
| `player, target, item, targetItem` | Cleanup bilateral | `true` (trade confirmado) |

## 🔧 Estrutura de Funcionalidades

### Função Principal (Callback)

#### **playerOnTradeAccept(player, target, item, targetItem)**

```lua
function callback.playerOnTradeAccept(player, target, item, targetItem)
	player:closeForge()
	target:closeForge()
	player:closeImbuementWindow()
	target:closeImbuementWindow()
	return true
end
```

**Propósito:** Entry point do callback. Realiza cleanup de UI e confirma trade.

**Fluxo de Execução:**

1. **Recebimento:** Callback disparado quando player clica "Accept Trade"
2. **Cleanup Bilateral:**
   - `player:closeForge()` - Fecha forge do açador
   - `target:closeForge()` - Fecha forge do alvo
   - `player:closeImbuementWindow()` - Fecha imbuement do açador
   - `target:closeImbuementWindow()` - Fecha imbuement do alvo
3. **Confirmação:** Retorna `true` para indicar que trade pode proceder

**Parâmetros:**
- `player` - Player que está aceitando a trade
- `target` - Outro player na trade (trade partner)
- `item` - Item offered by player
- `targetItem` - Item offered by target

**Retorno:**
- `true` - Trade é aceita e finalizada
- `false` - Trade é rejeitada (não implementado aqui)

## 🎯 Padrões & Boas Práticas

### Padrão 1: Bilateral State Cleanup

**Técnica:** Aplicar cleanup a ambos os players da transação.

```lua
-- Cleanup player
player:closeForge()
player:closeImbuementWindow()

-- Cleanup target (simétrico)
target:closeForge()
target:closeImbuementWindow()
```

**Vantagem:** Garante estado consistente em ambos. Previne UI trash.

**Aplicação:** Qualquer transação multi-player (trade, duel, marriage).

---

### Padrão 2: Sequential Cleanup (Forge then Imbuement)

**Técnica:** Executar cleanup em ordem específica (mais importante primeiro).

```lua
player:closeForge()        -- Fecha Forge (main tool)
player:closeImbuementWindow()  -- Depois Imbuement (secondary tool)
```

**Vantagem:** Evita states inconsistentes. Ordem importa para dependencies.

**Aplicação:** Quando cleanup tem dependencies (close dependent windows first).

---

### Padrão 3: Boolean Return for Confirmation

**Técnica:** Retornar true/false para indicar sucesso ou rejeição da ação.

```lua
-- Se tudo correu bem:
return true  -- Trade vai proceder

-- Se algo errou (hipotético):
return false  -- Trade é cancelada
```

**Vantagem:** Engine sabe se pode proceder. Simples, determinístico.

**Aplicação:** Qualquer ação que necessite aprovação do callback.

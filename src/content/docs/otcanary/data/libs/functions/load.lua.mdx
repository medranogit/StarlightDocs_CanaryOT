## 🛠️ Informações do Arquivo

Arquivo de bootstrap que carrega todos os 32 módulos de funções da pasta `data/libs/functions/` em ordem correta. Responsável por garantir que todas as extensões de class, helpers globais, e utilitários estejam disponíveis quando scripts de eventos, actions, talkactions, e sistemas customizados executarem.

<Aside type="tip">
O arquivo `load.lua` é o **entry point de inicialização** da camada de utilidades do servidor. Sua ordem de carregamento é crítica para resolver dependências (ex: `functions.lua` deve carregar antes de `boss_lever.lua` que usa funções dele).
</Aside>

## 📄 Visão Geral do Código

### Resumo Executivo

O arquivo `load.lua` implementa **padrão de bootstrap simples**: 32 chamadas `dofile()` que carregam módulos em ordem. Diferentemente de sistemas complexos com registry dinâmico, este padrão é **explícito e debugável**.

A ordem de carregamento segue estratégia de **dependência inversa** (carregar dependências antes de dependentes):

1. **Utilidades Básicas** (bit, bitwise_flags, fs, string, tables)
2. **Dados e Estruturas** (constants, queue, set)
3. **Classes Nativas Estendidas** (item, itemtype, creature, monster, player, party)
4. **Sistemas de Boss e Combate** (combat, boss_lever, lever, spawn)
5. **Utilitários Avançados** (functions, game, gematelier, container)
6. **Sistemas Especializados** (teleport, modal_window_helper, quests, pronouns)

## 🔄 Ordem de Carregamento Explicada

### Fase 1: Primitivas (Sem Dependências)
```lua
dofile(CORE_DIRECTORY .. "/libs/functions/bit.lua")              -- 1. Operações bitwise
dofile(CORE_DIRECTORY .. "/libs/functions/bitwise_flags.lua")    -- 2. Bitwise alternativo
dofile(CORE_DIRECTORY .. "/libs/functions/boss_lever.lua")       -- 3. Boss system (early para debug)
dofile(CORE_DIRECTORY .. "/libs/functions/combat.lua")           -- 4. Combat extensions
dofile(CORE_DIRECTORY .. "/libs/functions/constants.lua")        -- 5. Constantes globais
dofile(CORE_DIRECTORY .. "/libs/functions/container.lua")        -- 6. Container loot
```

**Observação**: `boss_lever.lua` carregado 3º apesar de usar `functions.lua` (carregado depois) - possível **bug de ordem** ou `functions.lua` é carregado globalmente antes.

### Fase 2: Classes Nativas Básicas
```lua
dofile(CORE_DIRECTORY .. "/libs/functions/creature.lua")
dofile(CORE_DIRECTORY .. "/libs/functions/fs.lua")
dofile(CORE_DIRECTORY .. "/libs/functions/functions.lua")        -- 9. Maior módulo
dofile(CORE_DIRECTORY .. "/libs/functions/game.lua")             -- 10. Game extensions
```

### Fase 3: Especialistadas
```lua
dofile(CORE_DIRECTORY .. "/libs/functions/gematelier.lua")       -- 11. Gem system
dofile(CORE_DIRECTORY .. "/libs/functions/item.lua")             -- 12. Item method
dofile(CORE_DIRECTORY .. "/libs/functions/itemtype.lua")         -- 13. ItemType method
dofile(CORE_DIRECTORY .. "/libs/functions/lever.lua")            -- 14. Lever system
```

## 🔧 Padrões de Uso

### Integração no Bootstrap

```lua
-- No arquivo data/core.lua ou data/init.lua:
dofile(CORE_DIRECTORY .. "/libs/functions/load.lua")

-- Agora todas as 32 bibliotecas estão disponíveis globalmente
print(Game.broadcastMessage)        -- ✓ Disponível
print(Lever)                        -- ✓ Disponível
print(Item.getType)                 -- ✓ Disponível
```

### Adicionando Novo Módulo

Se criar novo módulo `data/libs/functions/mynewlib.lua`:

1. Implementar as funções
2. Adicionar `dofile()` em `load.lua` na posição correta
3. Se tem dependências, colocar depois delas
4. Se outros dependem, colocar antes deles

```lua
-- Exemplo: adicionar modal_window_helper com dependência em functions.lua
-- Inserir depois de functions.lua (linha 9)
dofile(CORE_DIRECTORY .. "/libs/functions/functions.lua")
dofile(CORE_DIRECTORY .. "/libs/functions/my_custom_lib.lua")  -- Novo
dofile(CORE_DIRECTORY .. "/libs/functions/game.lua")
```

## ✅ Checkpoint de Aprendizagem

### Conceitos Principais

1. **Bootstrap Pattern**: Arquivo centralizador que inicializa dependências
2. **Explicit Loading Order**: Ordem literal é crítica para resolver dependências
3. **Global Namespace Pollution**: Todos 32 módulos populam global Lua
4. **No Lazy Loading**: Tudo é carregado upfront (vs. require() sob demanda)

### Stack Recomendado

Para novo desenvolvimento, seguir ordem:
1. Primitivas (bit, string, tables)
2. Dados (constants, structures)
3. Classes nativas (item, player, creature)
4. Sistemas (boss, combat, teleport)
5. Globais (functions, game)
6. Especializados (quests, modals)

## 📚 Conclusão

O arquivo `load.lua` é **orquestrador simples mas crítico** do servidor Canary. Sua lista de 32 `dofile()` carrega incrementalmente a pilha inteira de utilidades que makes possible o restante do codebase.

Apesar de explícito e debugável, o padrão de **ordem-literal** é frágil: mover uma linha pode quebrar a compilação. Sistemas moderinos usam registry dinâmico (ex: Lua 5.3+ `require()` com `package.path`), mas `dofile()` é mais simples e explícito.

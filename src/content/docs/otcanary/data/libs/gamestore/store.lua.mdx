## 🛠️ Informações do Arquivo

**Descrição**: Módulo **utilitário centralizado** que fornece 14 funções de query, validação e normalização para o sistema gamestore. Responsável por pesquisar categorias/ofertas pelo GameStore.Categories, recuperar histórico de transações do banco de dados, validar nomes (jogadores e capangas) seguindo regras sofisticadas de filtro de conteúdo, e normalizar dados de ofertas. Este é o **módulo "helper" fundamental** que todos os outros módulos dependem para funcionar.

**Caminho Original**: `data/libs/gamestore/store.lua`

**Dependências**:
- GameStore global (Categories, OfferTypes, States, DefaultDescriptions, etc)
- Database (db.query, db.storeQuery, Result)
- Lua string patterns (gmatch, match, find, split)
- Server objects (MonsterType, Npc)

<Aside>
Este módulo é **referência central** que abstrai queries complexas (ofertas com múltiplos IDs, outfits com sexo específico) e validações sofisticadas (nomes com palavras proibidas, caracteres inválidos). Sem ele, toda a lógica de busca dispersaria pelo código.
</Aside>

## 📄 Visão Geral do Código

### Resumo Executivo

O módulo store.lua é um **repositório de utilidades** que encapsula 14 funções divididas em 3 grupos: **queries de navegação** (buscar categoria/oferta pela estrutura GameStore.Categories), **acesso a banco de dados** (histórico de transações com paginação), e **validações de segurança** (nomes com proteção contra conteúdo ofensivo, SQL injection, nomes reservados). Notável por lidar com complexidades ocultas: ofertas podem ter IDs como números ou tabelas (outfit com male e female), histórico é paginado com ordering reverso, validação de nome é sofisticada com regex múltiplos e listas de palavras proibidas.


## Detalhes das Funções Globais

### 1. getCategoryByName(name)

Procura categoria por nome (case-insensitive).

**Parâmetros**:
- name (string): Nome da categoria a buscar

**Retorna**: 
- (table): Categoria encontrada ou nil

**Lógica**:

```lua
for k, category in ipairs(GameStore.Categories) do
    if category.name:lower() == name:lower() then
        if not category.offers then  -- Se vazia, recurse
            return GameStore.getCategoryByName(category.subclasses[1])
        end
        return category
    end
end
return nil
```

**Peculiaridade**: Se categoria vazia, busca subclasses[1] recursivamente

### 2. getCategoryByOffer(id)

Procura categoria que contém uma oferta específica (busca reversa).

**Parâmetros**:
- id (number): ID da oferta

**Retorna**: 
- (table): Categoria encontrada ou nil

**Handleamento de Múltiplos ID Types**:

```lua
-- Tipo 1: ID simples (number)
if type(offer.id) == "number" then
    if offer.id == id then return category end

-- Tipo 2: ID tabela (outfit: {male: X, female: Y})
elseif type(offer.id) == "table" then
    for m, offerId in pairs(offer.id) do
        if offerId == id then return category end
    end
end
```

### 3. getOfferById(id) - FUNÇÃO COMPLEXA

Procura oferta por ID com suporte a 3 tipos de estrutura de ID.

**Parâmetros**:
- id (number): ID da oferta

**Retorna**: 
- (table): Oferta encontrada (possivelmente modificada) ou nil

**Tipo 1: ID Simples**

```lua
if type(offer.id) == "number" then
    if offer.id == id then return offer end
end
```

**Tipo 2: ID Tabela (Outfit)**

```lua
elseif type(offer.id) == "table" and 
       (offer.type == OFFER_TYPE_OUTFIT or offer.type == OFFER_TYPE_OUTFIT_ADDON) then
    for m, offerId in pairs(offer.id) do
        if offerId == id then return offer end
    end
end
```

**Tipo 3: ID Múltiplo (Multi-Offer com Prices Paralela)**

```lua
elseif type(offer.id) == "table" then
    local newoffer = offer
    for i = 1, #offer.id do
        local offerId = offer.id[i]
        if offerId == id then
            -- Clonar oferta com ID específico
            newoffer.id = offerId
            newoffer.price = offer.price[i]  -- Preço específico
            return newoffer
        end
    end
end
```

**Nota**: Tipo 3 modifica oferta retornada (ID e price sincronizados)

### 6. haveOfferRook(id)

Verifica se oferta específica existe em alguma categoria rook.

**Parâmetros**:
- id (number): ID da oferta

**Retorna**: 
- (boolean): true se ofertar existe em rook, nil caso contrário

### 7. insertHistory(accountId, mode, description, coinAmount, coinType)

Insere entrada de transação no histórico do banco de dados.

**Parâmetros**:
- accountId (number): ID da conta
- mode (number): Modo (0=normal, 1=gift, 2=refund)
- description (string): Descrição da transação
- coinAmount (number): Quantidade de moedas
- coinType (number): Tipo de moeda (Coin ou Transferable)

**Retorna**: 
- (boolean): Resultado da query

**SQL Executado**:

```lua
INSERT INTO store_history (
    account_id, mode, description, coin_type, coin_amount, time
) VALUES (
    accountId, mode, escapedDescription, coinType, coinAmount, os.time()
)
```

**Nota**: description é escaped com db.escapeString()

### 9. retrieveHistoryEntries(accountId, currentPage, entriesPerPage) - FUNÇÃO DATABASE

Recupera histórico paginado com ordering reverso (mais recente primeiro).

**Parâmetros**:
- accountId (number): ID da conta
- currentPage (number): Página requisitada (1-indexed)
- entriesPerPage (number): Entries por página

**Retorna**: 
- (table): Array de entradas

**Cálculo de Offset**:

```lua
local offset = currentPage > 1 and entriesPerPage * (currentPage - 1) or 0
```

**SQL Executado**:

```lua
SELECT * FROM store_history 
WHERE account_id = accountId 
ORDER BY time DESC 
LIMIT offset, entriesPerPage
```

**Estrutura de Entry Retornada**:

```lua
{
    mode = number,          -- 0/1/2
    description = string,
    amount = number,        -- coinAmount
    type = number,          -- coinType
    time = number           -- timestamp
}
```

### 12. normalizeOffer(offer) - FUNÇÃO MÚLTIPLA

Valida e normaliza todos os campos de uma oferta.

**Parâmetros**:
- offer (table): Oferta a normalizar

**Retorna**: 
- (table): Oferta normalizada

**Validações**:

#### Type

```lua
if type(offer.type) ~= "number" then
    offer.type = OfferTypes.OFFER_TYPE_NONE
end
```

#### CoinType

```lua
if offer.coinType == nil then
    offer.coinType = CoinType.Transferable  -- Default
else
    local isValidCoinType = false
    for _, value in pairs(CoinType) do
        if value == offer.coinType then
            isValidCoinType = true
            break
        end
    end
    if not isValidCoinType then
        error("Invalid coin type: " .. tostring(offer.coinType))
    end
end
```

#### State

```lua
offer.state = GameStore.resolveState(offer.state)
```

#### Description

```lua
if description == nil or description == "" then
    description = getDefaultDescription(offer.type, offer.count) or ""
end
offer.description = description
```

### 13. canUseHirelingName(name) - FUNÇÃO VALIDAÇÃO SOFISTICADA

**Parâmetros**:
- name (string): Nome do capanga

**Retorna**: 
- (table): Table with `ability` (boolean) and `reason` (string)

**Validação 1: Comprimento**

```lua

    return result
end
```

**Validação 2: Espaço no Início**

```lua

    result.reason = "Can't have whitespace at begin."
    return result
end
```

**Validação 3: Caracteres Inválidos**

```lua

    result.reason = "Has invalid characters"
    return result
end
```

**Validação 4: Múltiplos Espaços**

```lua

local count = 0
for _ in match do count = count + 1 end

if count > 1 then
    result.reason = "More than 1 whitespace."
    return result
end
```

**Validação 5: Palavras Proibidas**

```lua
local words = { "owner", "gamemaster", "admin", ... }
local split = name:split(" ")

-- Check palavras diretas
for _, word in ipairs(words) do
    for _, nameWord in ipairs(split) do
        if nameWord:lower() == word then
            result.reason = "You can't use word '" .. word .. "'"
            return result
        end
    end
end

-- Check com espaços removidos
local tmpName = name:gsub("%s+", "")
for _, word in ipairs(words) do
    if tmpName:lower():find(word) then
        result.reason = "You can't use word '" .. word .. "' with whitespace"
        return result
    end
end
```

## 🔄 Padrões de Uso

### Padrão 1: Buscar Categoria por Nome

```lua
local store = require("gamestore.store")

function openCategoryByName(playerId, categoryName)
    local category = store.getCategoryByName(categoryName)
    if not category then
        return false, "Category not found"
    end
    senders.sendShowStoreOffers(playerId, category)
    return true
end
```

```lua

    if not offer then
        return nil, "Offer not found"
    end
    
    -- offer pode ter ID modificado (tipo 3)
    return offer

```

### Padrão 3: Validar Zonas Rook

```lua
local store = require("gamestore.store")

function validateRookAccess(player, offerId)
    if player:getVocation():getId() == 0 then  -- Rook
        if not store.haveCategoryRook() then
            return false, "No rook category"
        end
        if not store.haveOfferRook(offerId) then
            return false, "Offer not in rook"
        end
    end
    return true
end
```

### Padrão 4: Recuperar Histórico com Paginação

```lua
local store = require("gamestore.store")

function getPlayerHistory(playerId, page)
    local player = Player(playerId)
    local accountId = player:getAccountId()
    local entriesPerPage = 10
    
    local totalPages = store.retrieveHistoryTotalPages(accountId)
    local entries = store.retrieveHistoryEntries(accountId, page, entriesPerPage)
    
    return {
        entries = entries,
        currentPage = page,
        totalPages = totalPages
    }
end
```

### Padrão 5: Validar e Normalizar Oferta


## 📚 Conclusão

O módulo `store.lua` é exemplo fino de **centralização de lógica** que torna código dependente mais limpo e testável. As complexidades ocultas - ofertas com IDs polimórficos, busca recursiva em subclasses, validações de nome sofisticadas com 10+ regras - são toda encapsuladas aqui, permitindo que parsers.lua, purchases.lua e senders.lua remainecem focados em responsabilidades principais.

Dois patterns particularmente notáveis: **ID Polimórfico** em getOfferById que transparentemente handleia numbers vs tabelas outfit vs multi-offers com preços paralelos é excelente exemplo de abstração graceful. As **validações de nome** (especialmente canChangeToName com 9 validações cascata) demonstram como proteger contra conteúdo impróprio, nomes reservados e exploração através de spacing.

O design database-aware (retrieveHistoryEntries com paginação e ORDER BY DESC) mostra maturidade de sistema de produção. Estudando este módulo, compreende-se importância de "utility modules" bem projetadas que abstraem queries comuns, prevenindo duplicação através do codebase inteiro.

<Aside type="tip">

</Aside>

<Aside type="caution">
**Atenção Crítica**:
- canChangeToName é muito sofisticada - mudanças podem quebrar validação de nomes
- Validações de ID (offer.id como table vs number) são críticas - mudar torna getOfferById frágil
- db.escapeString() é OBRIGATÓRIO em insertHistory - sem ele, SQL injection possível
- retrieveHistoryEntries usa DESC ordering - mudança inverte histórico
- getDefaultDescription usa math.random - pode ter inconsistência se chamado em loop rapido
- resolveState com error() quebra execução - tratante appropriadamente em caller
</Aside>

<Aside type="note">
**Notas de Manutenção**:
- getCategoryByName com subclasses é recursivo - testar circularidade
- getOfferById modifica oferta tipo 3 - sempre clonar se não quiser side effects
- Palavras proibidas em ambas funções nome são hardcoded - centralizar se mudar frequente
- retrieveHistoryTotalPages sem página limit - pode ser slow com muitas transações
- normalizeOffer não valida price/count - adicionar se necessário
- canUseHirelingName &lt;= 18 chars, canChangeToName &lt;= 29 chars - limites distintos por design
- SQL LIMIT offset, limit - sempre validar offset > 0 para prevenir bug paginação
</Aside>

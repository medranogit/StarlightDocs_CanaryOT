## 🛠️ Informações do Arquivo

**Descrição**: Módulo de **protocolo de rede** que encapsula toda a comunicação servidor→cliente do sistema gamestore. Responsável por serializar dados de ofertas, transações e estados em mensagens NetworkMessage com suporte a protocolo duplo (cliente < v1200 e >= v1200). Este é o módulo de **abstração de rede** que transforma lógica Lua em pacotes binários entendidos pelo cliente Tibia.

**Caminho Original**: `data/libs/gamestore/senders.lua`

**Dependências**:
- gamestore.helpers (convertType, useOfferConfigure)
- GameStore global (constantes, categories, utilities)
- NetworkMessage API (core de comunicação)

<Aside>
Este módulo é o **inverso de parsers.lua**: enquanto parsers recebe mensagens do cliente e despacha lógica, senders pega resultados de lógica e envia mensagens estruturadas de volta. Sem este módulo, cliente nunca vê ofertas, saldos ou confirmações.
</Aside>

## 📄 Visão Geral do Código

### Resumo Executivo

O módulo `senders.lua` implementa **13 funções de envio de protocolo** que convertem dados Lua em mensagens NetworkMessage binárias. Notável por suportar **versioning duplo** (protocolo antigo vs novo com diferentes estruturas), lidar com **preços dinâmicos** (EXPBOOST, NAMECHANGE), gerenciar **disable reasons com índices** para referência eficiente e integrar **visuais de tryon** que mostram previews dinâmicas de outfit/hireling ao jogador. O módulo demonstra design sofisticado de protocolo binário onde cada campo tem posição precisa e alguns campos são opcionais por versão cliente.

## Detalhes das Funções Globais

### 1. getCategoriesRook() - FUNÇÃO HELPER

Filtra categorias disponíveis apenas para Rook de Rookgaard.

**Retorna**: 
- (table, number): Tabela de categorias rook + contagem

**Lógica**:
```lua
for i, v in pairs(GameStore.Categories) do
    if v.rookgaard then
        tmpTable[#tmpTable + 1] = v
        count = count + 1
    end
end
```

**Uso Interno**: Chamada por openStore quando vocation == 0 (rook)

### 2. openStore(playerId) - FUNÇÃO CRÍTICA

Abre interface de loja principal enviando lista de categorias ao cliente.

**Parâmetros**:
- playerId (number): ID do jogador

**Validações**:
- Player existe e conectado
- GameStore.Categories está definido

**Versionamento**:

```lua
local oldProtocol = player:getClient().version < 1200
-- v1200+ suporta mais features
-- < v1200 suporta apenas base
```

**Lógica de Categorias**:

```lua
if player:getVocation():getId() == 0 then
    GameStoreCategories, GameStoreCount = getCategoriesRook()
else
    GameStoreCategories, GameStoreCount = GameStore.Categories, #GameStore.Categories
end
```

**Serialização (cada categoria)**:

| Campo | Tipo | Versão | Descrição |
|---|---|---|---|
| category.name | String | Ambas | Nome da categoria |
| category.description | String | oldProtocol | Descrição (só antigo) |
| category.state | Byte | Ambas | Estado (STATE_NONE, STATE_SALE, etc) |
| icons.size | Byte | Ambas | Número de ícones (max 255) |
| icons[] | String[] | Ambas | Array de ícones |
| category.parent | String ou U16(0) | Ambas | Categoria pai ou 0 |

**Efeito Final**:
1. Envia S_OpenStore opcode
2. Enviada contagem de categorias
3. Para cada categoria: nome, description, state, icons, parent
4. Agenda `sendStoreBalanceUpdating` para mostrar saldo

### 3. sendOfferDescription(player, offerId, description)

Envia descrição de oferta com opcode baixo nível 0xEA.

**Parâmetros**:
- player (userdata): Objeto jogador
- offerId (number): ID da oferta
- description (string): Descrição em texto

**Serialização**:
```lua
msg:addByte(0xEA)  -- Opcode específico
msg:addU32(offerId)
msg:addString(description)
```

**Nota**: Função especializada, raramente chamada diretamente (usado por sendShowStoreOffers)

### 4. sendShowStoreOffers(playerId, category, redirectId) - FUNÇÃO MÁS COMPLEXA

Envia lista de ofertas de uma categoria com suporte completo a disable reasons, preços dinâmicos, visuals de tryon e estados de venda.

**Parâmetros**:
- playerId (number): ID do jogador
- category (table): Categoria com ofertas
- redirectId (number, opcional): ID para navegação

**Retorna**: 
- (boolean): false se validações falham

**Validações Iniciais**:
- Player existe
- Category tem data válida
- Limit ofertas: 65535 normal, 30 para oldProtocol

**Fase 1: Grouping de Ofertas**

Agrupa ofertas por nome (para subitens):

```lua
for k, offer in ipairs(category.offers) do
    if not offers[name] then
        offers[name] = {
            offers = {},
            state = offer.state,
            id = offer.id,
            type = offer.type,
            icons = offer.icons,
            basePrice = offer.basePrice,
            description = offer.description
        }
    end
    table.insert(offers[name].offers, offer)
end
```

**Fase 2: Disable Reasons**

Coleta motivos de desabilitação únicos e indexa:

```lua
local canBuy = player:canBuyOffer(offer)
if canBuy.disabled == 1 then
    -- Procura índice existente
    if index não encontrado then
        table.insert(disableReasons, canBuy.disabledReason)
        offer.disabledReadonIndex = #disableReasons
    end
end
```

**Serialização de Pacote**:

```
[Opcode: S_StoreOffers]
[Category Name: String]
[Redirect ID: U32] (se não oldProtocol)
[Window Type: Byte 0]
[Collections Size: Byte 0]
[Collection Name: U16 0]
[Disable Reasons Count: U16]
  ├─ [Reason 1: String]
  ├─ [Reason 2: String]
  └─ [...]
[Offers Count: U16]
  ├─ [Offer Group 1]
  │  ├─ Offer Name: String
  │  ├─ Suboffers Count: Byte
  │  ├─ Description (via callback)
  │  └─ [Each Suboffer]
  │     ├─ ID: U32
  │     ├─ Count/Charges: U16
  │     ├─ Price: U32 (dinâmico para EXPBOOST/NAMECHANGE)
  │     ├─ CoinType: Byte
  │     ├─ Disabled: Byte (0 ou 1)
  │     ├─ Disable Reason Index: U16 (se disabled)
  │     ├─ State: Byte (com validUntil se SALE)
  │     ├─ Visual Type: Byte (SHOW_*)
  │     │  ├─ SHOW_NONE: Icon String
  │     │  ├─ SHOW_MOUNT: Mount ClientID U16
  │     │  ├─ SHOW_ITEM: ItemType U16
  │     │  ├─ SHOW_OUTFIT: LookType U16 + Cores
  │     │  └─ SHOW_HIRELING: Sex + LookTypes + Cores
  │     ├─ TryOn Type: Byte
  │     ├─ Collection: U16 (0)
  │     ├─ Popularity: U16 (0)
  │     ├─ State New Until: U32 (0)
  │     └─ Requires Configure: Byte
  └─ [...]
[Too Many Results: Byte] (se categoria == "Search")
```

**Preço Dinâmico**:

```lua
if offer.type == OFFER_TYPE_EXPBOOST then
    local purchaseExpCount = playerKV:get(expBoostCount) or 0
    xpBoostPrice = ExpBoostValues[purchaseExpCount]
elseif offer.type == OFFER_TYPE_NAMECHANGE and player:kv():get("namelock") then
    nameLockPrice = 0  -- Bonus: free
end
```

**Sales Handling**:

```lua
if offer.state == STATE_SALE then
    local daySub = offer.validUntil - os.date("*t").day
    if daySub >= 0 then
        msg:addByte(STATE_SALE)
        msg:addU32(os.time() + daySub * 86400)
        msg:addU32(offer.basePrice)
        haveSaleOffer = 1
    else
        msg:addByte(STATE_NONE)  -- Expirado
    end
end
```

**Visual Types (via convertType)**:

| Type | Serialização | Dados |
|---|---|---|
| SHOW_NONE | Ícone | String icon[1] |
| SHOW_MOUNT | ClientID | U16 + TryOn=1 |
| SHOW_ITEM | ItemType | U16 |
| SHOW_OUTFIT | LookType + Cores | U16 + 4 bytes + TryOn=1 |
| SHOW_HIRELING | Sex + LookTypes + Cores | Byte sex + 2 U16 + 4 bytes |

### 5. sendShowStoreOffersOnOldProtocol(playerId, category) - BACKWARDS COMPAT

Versão simplificada para clients < v1200 com limitações.

**Limitações Protocol Antigo**:
- Max 30 ofertas por categoria
- Sem suporte a transferable coins (UI)
- Sem redirect, collections, popularity
- Formato visual diferente (mount=icon.png, outfit=2 icons)
- Disable reasons como strings simples (não índices)

**Filtragem de Ofertas**:

```lua
-- Bloqueia ofertas que não são COIN type
if not offer.coinType or offer.coinType == CoinType.Coin then
    count = count + 1
end
```

**Serialização**:

```
[Opcode: S_StoreOffers]
[Category Name: String]
[Offers Count: U16]
  ├─ [Offer 1]
  │  ├─ Name: String (com count "50x ")
  │  ├─ Description: String
  │  ├─ Price: U32 (dinâmico)
  │  ├─ State: Byte (com validUntil se SALE)
  │  ├─ Disabled: Byte (0 ou 1)
  │  ├─ Disable Reason: String (se disabled)
  │  └─ Visual:
  │     ├─ MOUNT (1): "name.png"
  │     ├─ OUTFIT (2): 2 icon strings
  │     └─ OTHER: icon array
  └─ [Suboffers: U16 0]
```

### 6. sendStoreTransactionHistory(playerId, page, entriesPerPage)

Envia histórico paginado de transações do jogador.

**Parâmetros**:

```lua
local entries = GameStore.retrieveHistoryEntries(accountId, page, entriesPerPage)
```

### 9. sendStoreBalanceUpdating(playerId, updating)

Sinaliza que saldo está sendo atualizado (UI lock/unlock).

- playerId (number): ID do jogador
- updating (boolean): true = começando atualização, false = terminado

**Serialização**:


```lua

    senders.sendShowStoreOffers(playerId, category, 0)
```

### Padrão 3: Versionamento Protocol

```lua
local senders = require("gamestore.senders")

function sendOfferList(playerId, category)
    local player = Player(playerId)
    local oldProtocol = player:getClient().version < 1200
    
    if oldProtocol then
        senders.sendShowStoreOffersOnOldProtocol(playerId, category)
    else
        senders.sendShowStoreOffers(playerId, category)
    end
end
```

### Padrão 4: Feedback de Transação

```lua
local senders = require("gamestore.senders")

function completePurchase(playerId, offer)
    senders.sendStoreBalanceUpdating(playerId, true)

    senders.sendStorePurchaseSuccessful(playerId, "Purchase successful!")

```

### Padrão 5: Solicitar Input Modal

```lua

function buyNameChange(playerId, offerId)
```

### Padrão 6: Histórico Paginado

```lua
function viewTransactionHistory(playerId, page)
```

### Padrão 7: Home Page com Banners

## 📚 Conclusão

O módulo `senders.lua` é exemplo fino de **abstração de protocolo binário** em servidor game, onde complexidade de versionamento duplo, preços dinâmicos e visuals complexos são encapsulados em interfaces limpas. A sofisticação não está em funções individuais, mas em **coordenação de detalhes**: desde preço dinâmico inteligente (EXPBOOST respeita limite, NAMECHANGE bonus com namelock) até visual de tryon que integra cores exatas de player atual.

O padrão de **disable reasons acumuladas e indexadas** é particularmente notável - reduz redundância em rede enviando motivos únicos uma vez e referenciando por índice. O suporte dual a versões antigas demonstra pragmatismo: sem `sendShowStoreOffersOnOldProtocol`, clientes antigos quebram completamente com ofertas renderizadas diferente.

Estudando este módulo, compreende-se como sistemas complexos mantêm-se através de **separação entre problema lógico (player.lua, purchases.lua) e transporte (senders.lua)**. Protocolo binário é puro detalhe de implementação - se mudar de TCP/UDP/WebSocket, interface senders permanece igual, apenas implementação interna de NetworkMessage muda.

<Aside type="tip">
**Dica de Integração**: Este módulo é parte do pipeline: parsers.lua → purchases.lua → senders.lua. Nunca chamar estas funções diretamente exceto através de scheduler (addPlayerEvent). Se modificar estrutura de dados (categorias, offers), adaptar serialização aqui obrigatoriamente - protocol quebra silenciosamente de outra forma.
</Aside>

<Aside type="caution">
**Atenção Crítica**:
- Protocol versioning é crítico - oldProtocol < v1200 tem limitações hard
- Preços dinâmicos (EXPBOOST, NAMECHANGE) DEVEM ser recalculados a cada envio
- Disable reasons são acumuladas em runtime - limpar entre categorias obrigatório
- Sale validation com validUntil - usar os.date("*t").day, não os.time()
- TryOn visual requer player's actual outfit colors - não usar defaults
- Grouping de ofertas por nome é crítica para UI correta - sem grouping, UI lag
- HomeOffers requer filtro offer.home - sem isso, home page vazia
- NetworkMessage must be cleaned (msg:delete()) após sendToPlayer
</Aside>

<Aside type="note">
**Notas de Manutenção**:

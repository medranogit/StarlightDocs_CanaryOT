# 📄 load.lua

Arquivo de carregamento (loader) responsável por executar o arquivo de funções globais durante a inicialização do servidor. Arquivo simples que utiliza `dofile()` para carregar `functions.lua`.

## 📋 Resumo Executivo

<Card title="O que este arquivo faz?" icon="info">

Arquivo extremamente simples com uma única responsabilidade:

**Carrega o arquivo `functions.lua` no contexto global do servidor.**

```lua
dofile(DATA_DIRECTORY .. "/startup/others/functions.lua")
```

**Efeito**:
- Executa `functions.lua` no escopo global
- Todas as 6 funções ficam disponíveis globalmente
- Permite que outras partes do código usem as funções de inicialização de mapa

**Padrão**: Separação entre "loader" e "implementação"
- `load.lua`: Apenas carrega
- `functions.lua`: Contém lógica

</Card>

**Componentes**:

| Parte | Tipo | Descrição |
|-------|------|-----------|
| `dofile()` | Função Lua | Executa arquivo Lua, retorna valores ou executa side effects |
| `DATA_DIRECTORY` | Constante Global | Path base para diretório de dados (ex: `/home/otserver/data/`) |
| `"/startup/others/functions.lua"` | String Path | Caminho relativo ao DATA_DIRECTORY |

**Resultado da Concatenação**:
```
DATA_DIRECTORY = "/home/otserver/data/"
+
"/startup/others/functions.lua"
=
"/home/otserver/data/startup/others/functions.lua"
```

**Execução do dofile()**:
1. Lê arquivo `functions.lua`
2. Compila Lua bytecode
3. Executa no contexto global
4. Todas as funções definidas ficam globais

**Retorno**: O retorno do último statement da função (se houver), ou `nil`

## 🎯 Padrão de Loader

<Card title="Por que separar em dois arquivos?" icon="lightbulb">

Este é um padrão comum em sistemas Lua complexos:

### Vantagens da Separação

| Vantagem | Descrição |
|----------|-----------|
| **Separação de Concerns** | Loader apenas carrega, implementação fica separada |
| **Rapidez** | Fácil localizar o arquivo que carrega sem ler toda a lógica |
| **Escalabilidade** | Múltiplos files de funções podem ser carregados aqui |
| **Manutenção** | Alterar path é rápido, lógica não muda |
| **Clareza** | Novo desenvolverdor vê imediatamente a estrutura |

### Padrão Extended

Se houvesse múltiplas dependências:

```lua
-- load.lua (versão estendida)
dofile(DATA_DIRECTORY .. "/startup/others/functions.lua")
dofile(DATA_DIRECTORY .. "/startup/others/helpers.lua")
dofile(DATA_DIRECTORY .. "/startup/others/constants.lua")
```

**Atual**: Apenas `functions.lua` é necessário

</Card>

## ⚙️ Contexto de Execução

<Card title="Ambiente de Execução" icon="settings">

### Escopo Global

Após `dofile()`, todas as funções estão no **escopo global**:

```lua
-- Dentro de outros scripts:
CreateMapItem(myTable)              -- ✅ Funciona
loadLuaMapAction(actionTable)       -- ✅ Funciona
updateKeysStorage(migrationTable)   -- ✅ Funciona
```

### Não há Encapsulamento

Sem return de tabela ou namespace:

```lua
-- ❌ NÃO seria necessary:
local functions = require("functions")
functions.CreateMapItem(...)

-- ✅ Direto:
CreateMapItem(...)
```

### Timing Importante

- Funções carregadas **durante startup**
- Disponíveis **antes** da inicialização do mapa
- Podem ser chamadas por **qualquer otro startup script**
- Requerem APIs básicas já inicializadas (Tile, Game, etc)

</Card>

## 🛡️ Considerações de Implementação

<Card title="Notas Técnicas" icon="shield">

### DATA_DIRECTORY Constant

- Definido pelo sistema Canary
- Tipicamente: `/home/otserver/data/` ou caminho absoluto
- Crítico estar correto para evitar "file not found"

### Erro Potencial

Se arquivo não existir:

```
[Error] Failed to load script: /startup/others/functions.lua
[Error] dofile: file not found or parse error
```

**Solução**: Verificar path, permissões, syntax do functions.lua

### Sem Tratamento de Erro

```lua
-- load.lua NÃO usa:
if dofile(...) then ... end
pcall(dofile, ...)
```

**Implicação**: Se `functions.lua` tiver erro, startup falha completamente.

**Vantagem**: Erros críticos não são silenciados.

### Ordem Não Importa (Neste Caso)

Porque `functions.lua` é self-contained:
- Não chama outras funções no load
- Não depende de outros loaders
- Apenas define funções

</Card>

## 📊 Use Cases

<Card title="Como e quando load.lua é acionado" icon="workflow">

### Scenario 1: Startup Normal do Servidor

```
1. Servidor inicia
2. Sistema de startup carrega todos os arquivos em /startup/others/
3. load.lua é executado
4. functions.lua é carregado
5. CreateMapItem, loadLuaMapAction, etc estão prontos
```

**Quando**:Cada vez que o servidor inicia

### Scenario 2: Reload Scripts

Se suporta reload durante runtime:

```
1. Admin executa comando "reload scripts"
2. Arquivos de startup são recarregados
3. load.lua executado novamente
4. Funções atualizadas (se tiveram mudanças)
```

**Potencial Problema**: Redefinir funções durante runtime

### Scenario 3: Limpeza

Se servidor tem cleanup:

```
1. Servidor em shutdown
2. load.lua não é executado novamente
3. Funções permanecem em memória até shutdown completo
```

</Card>

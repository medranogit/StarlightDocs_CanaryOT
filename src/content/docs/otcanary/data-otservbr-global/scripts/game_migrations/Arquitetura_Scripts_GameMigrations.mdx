# 🔄 Arquitetura - Game Migrations

Guia completo sobre a arquitetura e estrutura técnica dos scripts de **Game Migrations** do servidor OTServ Canary. Entenda como implementar transformações, migrações de dados e atualizações estruturais do jogo.

---

## 🎯 Sobre essa Pasta de Scripts

<Card title="O que é?" icon="information">
A pasta `data-otservbr-global/scripts/game_migrations/` contém scripts **Lua** que implementam **migrações de dados** - transformações únicas executadas uma única vez durante o *boot* do servidor. Cada migration move dados de um formato antigo para um novo formato, atualiza estruturas de dados, ou realiza operações administrativas que devem acontecer automaticamente sem intervenção manual. Migrations são críticas para manter a integridade dos dados quando o servidor é atualizado com mudanças estruturais.
</Card>

<Card title="Casos de Uso" icon="target">
Você utilizará essa pasta quando precisar:

- **Migrar dados para novo sistema**: Converter storage antigo para novo KV (key-value)
- **Estruturar dados de players**: Reorganizar informações de contas, achievements, quests
- **Atualizar configurações globais**: Resetar charms, remover sistemas obsoletos, limpar bugs
- **Converter diferentes formatos**: Storage → KV, bits → boolean, números → strings
- **Processar em lote**: Aplicar transformações a todos os players automaticamente
- **Executar uma única vez**: Garantir que operações críticas rodem apenas no boot
- **Preservar dados antigos**: Ler dados legados e convertê-los para novo sistema
- **Auditoria e logging**: Registrar o que foi migrado para rastreamento
- **Sincronização de dados**: Alinharem múltiplos sistemas relacionados
- **Cleanup automático**: Remover dados obsoletos após migração bem-sucedida
</Card>

<Card title="Estrutura da Pasta" icon="list">
A pasta `scripts/game_migrations/` é organizada por **data/hora de criação**:

```
game_migrations/
├── 20231128213358_move_hireling_data_to_kv.lua
├── 20241708000535_move_achievement_to_kv.lua

```

**Padrão de Nomeação**: `[TIMESTAMP]_[DESCRIÇÃO].lua`
- TIMESTAMP: Identifica ordem de execução
- DESCRIÇÃO: Explica o que a migration faz
- Cada migration é registrada automaticamente no sistema

**Total**: 5 scripts documentados, cobrindo sistemas de hirellings, achievements, VIP, quests e charms.

## 🔍 Estrutura Geral

<Card title="O que é um Script de Migration?" icon="document">

Um **Game Migration** é um script que:
- **Executa uma única vez** no boot do servidor
- **Transforma dados** de um formato antigo para novo
- **Processa todos os players** automaticamente
- **Registra progresso** com logging detalhado
- **Garante integridade** dos dados após execução
- **Não pode ser executado novamente** (idempotência)

### Estrutura Básica

```lua
-- 1. Criar função de transformação
local function migrateDataForPlayer(player)
    -- Lógica de migração aqui
    return true  -- Sucesso
end

-- 2. Criar instância Migration
local migration = Migration("TIMESTAMP_description")

-- 3. Implementar callback onExecute
function migration:onExecute()
    self:forEachPlayer(migrateDataForPlayer)
end

-- 4. Registrar
migration:register()
```

### Parâmetros da Função de Callback

```lua
function migrateDataForPlayer(player)
    --
    -- player: Objeto Player a ser migrado
    --   - player:getName()  (nome do player)
    --   - player:getLevel()  (nível)
    --   - player:getStorageValue(key)  (ler storage antigo)
    --   - player:setStorageValue(key, value)  (resetar storage antigo)
    --   - player:kv()  (novo sistema KV - account level)
    --   - player:questKV(questName)  (KV específico de quest)
    --   - Métodos específicos do sistema (addAchievement, enableHirelingOutfit, etc)
    --
    -- Return: true = sucesso, false = erro (interrompe para este player)

    if not player then
        return false
    end

    -- Implementação
    return true
end
```

### Ciclo de Execução

```
Server Boot (Inicia)
    ↓
Game Migrations carregados (ordem por TIMESTAMP)
    ↓
Para cada migration registrada:
    ↓
    Para cada player online/offline:
        ↓
        migration:onExecute() chamada
        ↓
        callback executado para player
        ↓
        Resultado registrado (sucesso/erro)
    ↓
Migration marcada como completa
    ↓
Próxima migration ou servidor pronto
```

### Métodos Disponíveis

```lua
local migration = Migration("timestamp_name")

-- Iterar sobre todos os players
function migration:onExecute()
    self:forEachPlayer(function(player)
        -- Executado para cada player (online ou offline)
    end)
end

-- Acessar contexto de migration
function migration:onExecute()
    -- self:migrationId()  - Retorna ID único
    -- self:executed()  - Verifica se já rodou
end

migration:register()  -- Registra para ser executada
```

## 🔄 Ciclo de Vida de Migrations

<Card title="Quando e Como Migrations Executam" icon="clock">

### Fase 1: Carregamento

```lua
-- Ao iniciar o servidor, todas as migrations em game_migrations/ são carregadas
-- Ordenadas por TIMESTAMP (ordem crescente)
-- Cada uma é registrada com migration:register()
```

### Fase 2: Execução

```lua
-- Se ainda não foi executada (checado no banco de dados):
-- 
-- 1. Logger registra inicio
-- 2. Migration:onExecute() é chamada
-- 3. forEachPlayer() itera todos os players
-- 4. Callback executado para cada player
-- 5. Erros são capturados e logados
-- 6. Logger registra conclusão + estatísticas
-- 7. Migration marcada como completa no banco
```

### Fase 3: Idempotência

```lua
-- Uma migration NUNCA é executada duas vezes
-- Sistema verifica no banco: "Já rodou?"
-- Se sim: Ignora
-- Se não: Executa
-- 
-- Por isso o TIMESTAMP é importante:
-- - Identifica cada migration unicamente
-- - Define ordem de execução
-- - Garante não há duplicates
```

### Padrão de Logging

```lua
-- Todo migration deve registrar:
logger.info("[Migration] Starting migration...")
logger.debug("Processing player: {}", player:getName())
logger.warn("Unexpected value: {}", value)
logger.error("Failed to process player: {}", player:getName())
logger.info("[Migration] Completed. {} players processed.", count)
```

## 🏗️ Padrões de Implementação

<Card title="Padrões Comuns de Migrations" icon="wrench">

### Padrão 1: Storage para KV (Key-Value)

```lua
-- Migra dados de storage antigo para novo sistema KV

local OLD_STORAGE_KEY = 12345
local KV_KEY = "my-data"

local function migrateToKV(player)
    -- Lê do storage antigo
    local oldData = player:getStorageValue(OLD_STORAGE_KEY)
    
    if oldData > 0 then
        logger.debug("Migrating data for player: {}", player:getName())
        
        -- Escreve para novo KV
        player:kv():set(KV_KEY, oldData)
        
        -- Reseta storage antigo (limpeza)
        player:setStorageValue(OLD_STORAGE_KEY, -1)
    end
    
    return true
end

local migration = Migration("20250101000000_storage_to_kv")

function migration:onExecute()
    self:forEachPlayer(migrateToKV)
end

migration:register()
```

## 🔑 Sistemas KV vs Storage

<Card title="Entendendo a Transição de Storage para KV" icon="layers">

### Sistema Antigo: Storage

```lua
-- Storage: Números inteiros simples (podem ser bits)
-- Chave: inteiro (ex: 28800)
-- Valor: inteiro (ex: 15, onde bits representam flags)
-- Escopo: Player global

-- Exemplo 1: Bit flagging
local flags = player:getStorageValue(28800)  -- Valor: 15 (binário: 1111)
if hasBitSet(flags, 1) then        -- Bit 0 ativo?
    -- Tem BANKER skill
end

-- Exemplo 2: Simples estado
local vipStatus = player:getStorageValue(150001)
if vipStatus > 0 then  -- 1 = VIP, -1 = não VIP
    -- É VIP
end

-- Limitações:
-- - Apenas inteiros
-- - Sem tipo de dados complexos
-- - Difícil para muitos dados relacionados
-- - Em escopo flat (sem hierarquia)
```

### Sistema Novo: KV (Key-Value)

```lua
-- KV: Pares chave-valor com estrutura hierárquica
-- Chave: String (ex: "vip-system", "achievements/progress")
-- Valor: Qualquer tipo (string, número, boolean, JSON)
-- Escopo: Múltiplos (player, account, quest, etc)

-- Exemplo 1: Account-scoped
player:kv():scoped("account"):set("vip-system", true)

-- Exemplo 2: Quest-specific
player:questKV("my-quest"):set("completed", true)
player:questKV("my-quest"):set("progress", 50)

-- Vantagens:
-- + Strings legíveis (não números)
-- + Hierarquia clara (account, quest, etc)
-- + Múltiplos tipos de dados
-- + Melhor para dados relacionados
-- + Mais fácil de entender no código
```

### Padrão de Migração

```lua
-- Lê do antigo storage simples → Escreve para novo KV estruturado

-- ANTES (Storage)
local isVipStorage = 150001
local vipValue = player:getStorageValue(isVipStorage)  -- Retorna: 1, -1, ou não definido

-- DEPOIS (KV)
player:kv():scoped("account"):set("vip-system", true)  -- Armazena boolean

-- Migration faz essa conversão:
local function migrateVIP(player)
    local isVipValue = player:getStorageValue(150001)
    if isVipValue > 0 then  -- Se era VIP no sistema antigo
        player:kv():scoped("account"):set("vip-system", true)
        player:setStorageValue(150001, -1)  -- Marca como migrado
    end
end
```

### Comparação Visual

| Aspecto | Storage Antigo | KV Novo |
|---------|---|---|
| **Tipo de Chave** | Inteiro (28800) | String ("vip-system") |
| **Tipo de Valor** | Inteiro | Qualquer tipo |
| **Estrutura** | Flat | Hierárquica (scoped) |
| **Legibilidade** | Números mágicos | Nomes claros |
| **Flexibilidade** | Limitada | Alta |
| **Use Case** | Flags simples | Dados complexos |

</Card>

```lua
local OLD_STORAGE = 99999

local function migratePlayerData(player)
    -- Validação
    if not player then
        return false
    end
    
    -- Ler dado antigo
    local oldValue = player:getStorageValue(OLD_STORAGE)
    
    -- Validar existência
    if oldValue <= 0 then
        return true  -- Nada para migrar
    end
    
    -- Transformar e escrever para novo sistema
    player:kv():set("my-key", oldValue)
    
    -- Limpar antigo
    player:setStorageValue(OLD_STORAGE, -1)
    
    -- Log
    logger.debug("Migrated player: {}", player:getName())
    
    return true
end

local migration = Migration("20250205143217_my_migration")

function migration:onExecute()
    self:forEachPlayer(migratePlayerData)
end

migration:register()
```

### Passo 5: Adicionar Logging

```lua
function migration:onExecute()
    local totalPlayers = 0
    local successCount = 0
    local errorCount = 0
    
    logger.info("[Migration {}] Starting...", migration:migrationId())
    
    self:forEachPlayer(function(player)
        totalPlayers = totalPlayers + 1
        
        if migratePlayerData(player) then
            successCount = successCount + 1
        else
            errorCount = errorCount + 1
            logger.warn("Failed to migrate: {}", player:getName())
        end
    end)
    
    logger.info("[Migration {}] Complete. Success: {}, Errors: {}", 
        migration:migrationId(), successCount, errorCount)
end
```

### Exemplo Completo

```lua
-- 20250205143217_migrate_vip_status.lua

local OLD_VIP_STORAGE = 150001
local KV_KEY = "vip-system"

-- Função base de migração
local function migrateVIPForPlayer(player)
    if not player then
        return false
    end
    
    -- Lê o valor antigo
    local oldVIPStatus = player:getStorageValue(OLD_VIP_STORAGE)
    
    -- Se não existia, nada para fazer
    if oldVIPStatus <= 0 then
        return true
    end
    
    -- Converte data antigo para novo formato
    local isVIP = oldVIPStatus > 0  -- Simples boolean
    
    -- Escreve para novo sistema
    player:kv():scoped("account"):set(KV_KEY, isVIP)
    
    -- Marca storage antigo como migrado (-1 = vazio)
    player:setStorageValue(OLD_VIP_STORAGE, -1)
    
    -- Log individual (debug level)
    logger.debug("Migrated VIP status for: {} (was {})", player:getName(), oldVIPStatus)
    
    return true
end

-- Criar migration
local migration = Migration("20250205143217_migrate_vip_status")

-- Executar para todos os players
function migration:onExecute()
    local totalProcessed = 0
    local totalMigrated = 0
    
    logger.info("[Migration {}] Starting VIP migration", migration:migrationId())
    
    self:forEachPlayer(function(player)
        totalProcessed = totalProcessed + 1
        
        if migrateVIPForPlayer(player) then
            totalMigrated = totalMigrated + 1
        else
            logger.error("Failed to migrate player: {}", player:getName())
        end
    end)
    
    logger.info("[Migration {}] Completed. Migrated: {}/{} players", 
        migration:migrationId(), totalMigrated, totalProcessed)
end

-- Registrar para ser executada automaticamente
migration:register()
```

## 🔧 Guia de Troubleshooting

<Card title="Problemas Comuns" icon="bug">

### Problema: Migration não executa

**Causa**: Arquivo não está em `game_migrations/` ou não tem `.register()` chamado  
**Solução**:
```lua
-- ✅ Correto
local migration = Migration("timestamp_name")

function migration:onExecute()
    self:forEachPlayer(function(player)
        -- implementação
    end)
end

migration:register()  -- Essencial!

-- ❌ Errado - Sem register()
local migration = Migration("timestamp_name")
-- ... (sem migration:register())
```

### Problema: Migration executa mas não faz nada

**Causa**: Iteração sobre `forEachPlayer()` está vazia ou silent  
**Solução**:
```lua
-- ✅ Correto - Verificar se players existem
function migration:onExecute()
    local count = 0
    self:forEachPlayer(function(player)
        count = count + 1
        logger.debug("Processing: {}", player:getName())
    end)
    logger.info("Processed {} players", count)
end

-- ❌ Errado - Sem verificação
function migration:onExecute()
    self:forEachPlayer(function(player)
        -- Silencioso, sem logs
    end)
end
```

### Problema: Storage antigo não resetado

**Causa**: Esqueceu de chamar `player:setStorageValue(oldKey, -1)`  
**Solução**:
```lua
-- ✅ Correto - Reseta storage antigo depois
local oldValue = player:getStorageValue(OLD_KEY)
if oldValue > 0 then
    player:kv():set("new-key", oldValue)
    player:setStorageValue(OLD_KEY, -1)  -- ← Importantíssimo!
end

-- ❌ Errado - Deixa storage antigo
-- Cria duplicação de dados!
local oldValue = player:getStorageValue(OLD_KEY)
player:kv():set("new-key", oldValue)
-- Storage antigo jamais é resetado
```

### Problema: Dados duplicados após migração

**Causa**: Migration rodou múltiplas vezes (não é idempotente)  
**Solução**:
```lua
-- ✅ Correto - Verifica se já foi migrado
if oldValue > 0 then  -- Só processa se não vazio
    -- Migra
    player:setStorageValue(oldKey, -1)  -- Marca como processado
end

-- ❌ Errado - Sempre processa
player:kv():set("key", player:getStorageValue(oldKey))
-- Se rodar 2x, duplica dados!
```

### Problema: Timestamp está duplicado

**Causa**: Dois arquivos com mesmo timestamp  
**Solução**:
```bash
# Timestamps devem ser únicos
❌ 20250205143217_migration1.lua
❌ 20250205143217_migration2.lua  (CONFLITO!)

✅ 20250205143217_migration1.lua
✅ 20250205143218_migration2.lua  (Incrementa 1 segundo)
```

### Problema: Migration perde player mid-process

**Causa**: Player desconectou durante migração, dados perdidos  
**Solução**:
```lua
-- ✅ Correto - Sempre valida player
local function migrate(player)
    if not player then  -- ← Essencial!
        return false
    end
    -- ... resto da lógica
    return true
end

-- ✅ Correto - forEachPlayer já lida com offline
-- Migrations podem processar até players offline (via banco)
self:forEachPlayer(function(player)
    -- player pode estar online ou offline
end)
```

### Problema: Logs não aparecem

**Causa**: Log level está alto (não mostra debug)  
**Solução**:
```lua
-- Use logger.info() em vez de logger.debug() para migrations importantes
logger.info("[Migration] Starting...")  -- ✅ Aparece sempre
logger.debug("Detail: {}", value)       -- ⚠️ Pode não aparecer
logger.warn("Warning")                  -- ✅ Aparece sempre
logger.error("Error")                   -- ✅ Aparece sempre
```

## 📖 Referência Rápida

<Aside type="tip">

**Estrutura Padrão de Migration**:
```lua
local migration = Migration("TIMESTAMP_description")

function migration:onExecute()
    self:forEachPlayer(function(player)
        -- Validar
        if not player then return false end
        
        -- Ler antigo
        local oldData = player:getStorageValue(OLD_KEY)
        if oldData <= 0 then return true end
        
        -- Escrever novo
        player:kv():set("key", oldData)
        
        -- Limpar antigo
        player:setStorageValue(OLD_KEY, -1)
        
        return true
    end)
end

migration:register()
```

**Métodos Comuns**:
- `Migration("id")` - Criar migration
- `migration:onExecute()` - Callback principal
- `self:forEachPlayer(callback)` - Iterar todos os players
- `player:getStorageValue(key)` - Ler storage antigo
- `player:setStorageValue(key, -1)` - Resetar storage
- `player:kv():set(key, value)` - Escrever KV novo
- `player:kv():scoped(scope):set(key, value)` - KV com escopo
- `migration:register()` - Registrar para execução

**Boas Práticas**:
- ✅ Sempre resete storage antigo (`-1`)
- ✅ Sempre valide se player existe
- ✅ Sempre faça log do processo
- ✅ Use timestamps únicos
- ✅ Teste com múltiplos players
- ✅ Seja idempotente (rode 1x)

**Ordem de Execução**:
- Migrações rodam em ordem de TIMESTAMP
- Nunca rodam 2x para mesma instância
- Executam durante boot do servidor
- Todos os players processados (online/offline)

</Aside>
